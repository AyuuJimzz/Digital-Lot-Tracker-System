---

## 📋 Executive Overview

This runbook defines a data-preserving rollout procedure for migrating the production database to support explicit sales-date provenance (`is_date_verified` and `date_provenance`), deploying the backend Zero-Trust guards, and performing post-rollout verification. No migration can guarantee zero data loss without a verified recovery plan.

### Core Objectives:
1. Prevent unverified or synthetic backfill dates from falsely inflating monthly dated sales charts.
2. Prevent unmigrated schemas from silently completing sales without explicit provenance tracking.
3. Preserve prior sale-date values in correction audit rows; reversals, resales, and migration reruns must not rewrite earlier sale transactions.
4. Establish defensive, non-destructive incident protocols (no blind restores, no automatic column drops).

## 🛠️ Rollout Step-by-Step Execution Sequence

The shell examples below use Bash syntax (Linux, Git Bash, or WSL); do not paste them directly into PowerShell. Confirm the execution host and database target before running any command.

### Phase 1: Full Production Database Backup (MANDATORY)

Create a point-in-time snapshot before running any DDL or migration scripts:

```bash
# Set timestamp and backup filename
BACKUP_FILE="backup_golden_dragon_pre_provenance_$(date +%Y%m%d_%H%M%S).sql"

# Execute mysqldump with transaction isolation
mysqldump -h <DB_HOST> -P <DB_PORT> -u <DB_USER> -p <DB_NAME> \
  --single-transaction \
  --quick \
  --triggers \
  --routines \
  --hex-blob > "$BACKUP_FILE"
```

**Verification Gate**:
- Verify file exists and has non-zero size: `ls -lh "$BACKUP_FILE"`
- Check that the dump includes the `transactions` table: `grep -m 1 "CREATE TABLE \`transactions\`" "$BACKUP_FILE"`. This is only a quick sanity check, not proof that the backup can be restored.
- Rehearse restoration in an isolated staging database before production migration; never restore a test dump over live data.
- **STOP CONDITION 1**: If backup fails, is empty, or outputs errors, **ABORT IMMEDIATELY**. Do not proceed to Phase 2.

---

### Phase 2: Read-Only Audit & Classification Review (`--plan`)

Run the conservative date provenance migration script in dry-run/plan mode:

```bash
cd back-end
node scripts/migrate_date_provenance.js --plan
```

**What the Plan Analyzes**:
1. `Total Transactions in Database`: Total rows in `transactions` table.
2. `Verified (explicit sold_on/audit/system)`: Legitimate completed sales with confirmed calendar dates.
3. `Known Backfills (synthetic)`: Legacy backfills (e.g. `notes = 'Reservation record'`, synthetic No Downpayment).
4. `Unknown (requires staff review)`: Undated or unconfirmed transactions requiring manual admin audit.
5. `Reversals / Cancellations`: Reversal audit transactions (e.g. `payment_type = 'Reversal'`).

---

### Phase 3: Human Review & Count Verification Gate

Inspect the output table generated by Phase 2:

```text
=============================================================================
📋 PRE-MIGRATION AUDIT BREAKDOWN
=============================================================================
Total Transactions in Database:      <TOTAL>
- Verified (via explicit sold_on):   <V_COUNT>  ➔ is_date_verified = 1
- Known Backfills (synthetic):       <KB_COUNT> ➔ is_date_verified = 0, 'unverified_backfill'
- Unknown (requires staff review):   <U_COUNT>  ➔ is_date_verified = 0, 'unknown_requires_review'
- Reversals / Cancellations:         <R_COUNT>  ➔ is_date_verified = 0, 'reversal'
=============================================================================
```

**Mathematical Invariant Check**:
$$\text{Total Transactions} = \text{Verified} + \text{Known Backfills} + \text{Unknown} + \text{Reversals}$$

- [ ] Confirm that $V + KB + U + R = \text{Total Transactions}$ (partition is mutually exclusive and exhaustive).
- [ ] Confirm that known synthetic backfills are NOT classified as verified.
- [ ] Confirm that legitimate completed sales (including `No Downpayment` sales with valid customer and lot link) are classified as verified.
- **STOP CONDITION 2**: If the partition sum does not equal total transactions, **ABORT IMMEDIATELY**. Investigate data anomalies before running migration.

---

### Phase 4: Additive Schema Migration (`migrateDateProvenance()`)

Once Phase 3 counts are approved by the team, apply the additive migration:

```bash
cd back-end
node scripts/migrate_date_provenance.js
node scripts/migrate_sale_date_audit.js
```

**Actions Executed**:
1. Checks if `is_date_verified` exists on `transactions`; if not, adds `TINYINT(1) NOT NULL DEFAULT 0`.
2. Checks if `date_provenance` exists on `transactions`; if not, adds `VARCHAR(50) NOT NULL DEFAULT 'unknown_requires_review'`.
3. Populates provenance categories according to verified criteria.
4. Leaves `transaction_date` and audit logs completely intact (zero timestamp mutations).
5. Creates the empty `sale_date_audit` table for future staff date corrections. Application code only inserts audit rows; database administrators must still protect this table from manual updates/deletes. The migration does not infer or backfill corrections made before this rollout.

**Idempotency Verification**:
Run the script a second time:
```bash
node scripts/migrate_date_provenance.js
node scripts/migrate_sale_date_audit.js
```
- It must report: `✅ Conservative migration applied successfully` with 0 duplicate column errors.

### Phase 5: Production Schema & Column Verification

Connect to the production MySQL database and run read-only verification queries:

```sql
-- 1. Verify column definitions exist
SHOW COLUMNS FROM transactions WHERE Field IN ('is_date_verified', 'date_provenance');
-- EXPECTED: Exactly 2 rows returned with correct types.

-- 2. Verify provenance distribution matches Phase 3 plan
SELECT date_provenance, is_date_verified, COUNT(*) as count
FROM transactions
GROUP BY date_provenance, is_date_verified;
-- EXPECTED:
-- - 'system_recorded', 'manual_audit', or 'verified': is_date_verified = 1
-- - 'unverified_backfill': is_date_verified = 0
-- - 'unknown_requires_review': is_date_verified = 0
-- - 'reversal': is_date_verified = 0

-- 3. Assert zero contamination
SELECT COUNT(*) as invalid_count
FROM transactions
WHERE is_date_verified = 1 AND date_provenance IN ('unverified_backfill', 'unknown_requires_review');
-- EXPECTED: exactly 0.

-- 4. Verify the correction audit table is available before deploying the new backend
SHOW TABLES LIKE 'sale_date_audit';
-- EXPECTED: exactly 1 row. The table can be empty before the first correction.
```

- **STOP CONDITION 3**: If `invalid_count > 0`, columns are missing, or `sale_date_audit` is missing, **STOP AND FREEZE WRITES**. Do NOT drop columns or perform blind restore. Proceed to Incident Protocol (Section 8).

## 🚨 Incident Protocol & Defensive Recovery (NO Blind Restores, NO DROP COLUMN)

If an anomaly, timeout, or unexpected error occurs during migration or rollout:

### ⚠️ Critical Warning on Full Database Restores
> [!CAUTION]
> **DO NOT execute an immediate full-database restore (`mysql < backup.sql`) unless catastrophic total loss has occurred.**
>
> A full backup restore overwrites the entire database to the backup timestamp, **permanently destroying any new customer registrations, reservation inquiries, payments, or employee logs created after the backup was taken.**

### Incident Response Rules:
1. **STOP WRITES & HALT DEPLOYMENT**:
   - Immediately pause new deployments.
   - If migration encounters an issue, leave existing data intact.
   - Do NOT run `DROP COLUMN` commands. Because the migration columns are additive and nullable/defaulted, existing read views remain functional.
2. **PRESERVE CURRENT DATA STATE**:
   - Do not delete, truncate, or drop tables or columns.
   - Do not execute destructive rollback scripts or blind restores.
3. **COLLECT TELEMETRY & DIAGNOSTICS**:
   - Check column existence first: `SHOW COLUMNS FROM transactions WHERE Field IN ('is_date_verified', 'date_provenance');`. Record whether zero, one, or both columns exist.
   - Inspect database and application logs for specific query errors or lock timeouts.
   - Check the total row count with `SELECT COUNT(*) FROM transactions;`. **Only if both provenance columns exist**, inspect their distribution:
     ```sql
     SELECT date_provenance, is_date_verified, COUNT(*)
     FROM transactions
     GROUP BY date_provenance, is_date_verified;
     ```
4. **HUMAN REVIEW & TARGETED RECONCILIATION (Based on Actual DB State)**:
   - Conduct a thorough human review of telemetry and the actual database state before deciding any recovery action.
   - **DO NOT DROP PROVENANCE COLUMNS**: Dropping `is_date_verified` or `date_provenance` permanently destroys historical provenance records. Furthermore, if these columns are missing, backend Zero-Trust guards (`lotStatusController` and `transactionsController`) will actively block any new sale completion and throw HTTP 409 migration-required errors.
   - Formulate a surgical, state-grounded recovery or forward-fix plan (e.g., re-running `migrate_date_provenance.js` after resolving data anomalies, or manually auditing ambiguous transactions) tailored directly to the actual inspected records.
